计算机体系结构：量化研究方法

L.8 MMU 的集成：融会贯通

前面介绍了参与地址转换的几种微结构部件，从两级 TLB 层次、页表遍历器到多种 MMU Cache。这些部件还与 load-store 队列、处理器 Cache 等其他微结构部件有重要的相互作用。总的来说，这些部件相互作用时会形成大量的间接关系，因此可能比较难理解。本节专门详细说明这些微结构部件之间的相互作用。当然，相互作用的具体情况取决于采用哪些微结构部件，例如 Cache 是物理 tag 还是虚拟 tag，页表遍历由硬件还是软件完成，等等。为了简化讨论，我们假设 MMU 与一个虚拟索引、物理 tag 的 L1 Cache 集成在一起，并采用硬件 PTW。

图 L.14　页遍历 Cache 和分页结构 Cache 所需的 Cache 个数、每项的 tag 位数和每项的数据位数。统一结构和分离结构的结果分开列出。注意，转换路径 Cache 既不属于统一结构，也不属于分离结构。所有复杂度分析都以三个参数表示：转换的级数 \(L\)，物理地址的位数 \(P\)，某一级页表索引中的偏移位数 \(N\)。以 x86-64 处理器为例，\(L\) 为 4，\(P\) 为 52，\(N\) 为 9。图内标注：Unified，统一；Split，分离；Page Walk Cache，页遍历 Cache；Paging Structure Cache，分页结构 Cache；Translation Path Cache，转换路径 Cache；每组的 Cache、Tag bits、Data bits 三行依次为 Cache 个数、每项 tag 位数、每项数据位数。

（1）load/store 队列与 TLB。 CPU 产生的访存请求先进入 load/store 队列。在各个微结构部件中，load/store 队列最先与地址转换硬件交互 [54, 55]。商用微处理器中 load/store 队列与 TLB 怎样交互，公开的资料很少。下面根据已发表的研究工作和专利 [54]，给出这种交互的一种合理的轮廓。

高性能处理器的一个标志，是需要做访存预测和访存消歧（disambiguation）[26]。预测阶段预先判断 store 与 load 之间会不会在运行时访问同一物理地址，从而形成相关，目的是提前防止出现正确性问题；消歧阶段随后确认所有预测都是正确的。两个阶段配合起来，一方面能够检测出同义词，即多个虚拟地址映射到同一物理地址的情况，另一方面又不让 TLB 处在前递的关键路径上。

图 L.15　store 缓冲、load 缓冲与 TLB 层次之间的交互。图中的圆圈表示访存相关预测和消歧过程的各个步骤。load 缓冲和 store 缓冲都为虚拟页号（VP）、物理页号（PP）和页内偏移位（PO）分别设置字段；页内偏移在虚拟地址空间和物理地址空间中相同，所以不必重复存放。store 缓冲另有数据字段，load 缓冲没有。两个缓冲都有年龄字段，记录 load 和 store 按程序顺序进入缓冲的先后。图内标注：Store Buffer，store 缓冲；Load Buffer，load 缓冲；Data，数据；Age，年龄；Rest of the MMU and memory hierarchy，MMU 的其余部分和存储层次。

图 L.15 给出了一种可行的机制。图中单独画出了 L1 TLB、load 缓冲和 store 缓冲；地址转换硬件的其余部分和存储层次也存在，只是没有画出。load 缓冲和 store 缓冲都为虚拟页号（VP）和物理页号（PP）各设一个字段。页内偏移在虚拟地址空间和物理地址空间中相同，所以只设一个页内偏移字段 PO。页内偏移的位数随基本页和超级页而不同，但 load 缓冲和 store 缓冲只要按最小的页留够位数即可。x86-64 系统中最小的页是 4 KB，因此 x86-64 的 load/store 缓冲中页内偏移字段需要 12 位。

图 L.15 画出了 store 和 load 的执行过程。每条 store 在查找 TLB 的同时，把自己的虚拟地址和数据写入 store 缓冲（步骤 a），这样 store 缓冲相应表项的虚拟页号、页内偏移和数据字段就都填好了。TLB 返回结果后，再把物理页号写入这个表项（步骤 b）。5

load 的执行过程也画在图 L.15 中。load 在访问 TLB 的同时，写入自己的虚拟页号和页内偏移位（步骤 c）。然后，每条 load 把自己的页内偏移位与 store 缓冲中所有比它老的 store 逐一比较（步骤 d）。如果现有表项中没有一个相符，就说明没有哪条 store 与这条 load 访问同一地址。如果某条较老的 store 地址还没有生成（页内偏移字段为空），就预测它与这条 load 之间没有相关。

页内偏移位相符时，load 接着比较高位。如果 load 的虚拟页号与 store 的虚拟页号相符（步骤 e），store 就把它的值前递给 load（步骤 g）。如果虚拟页号不符，load 再把自己的物理页号与 store 的物理页号比较；这时两条指令中只要有一条的 TLB 访问还没有返回转换结果，load 就停顿等待。物理页号相符，store 把数据前递给 load；物理页号不符，load 就确定了自己与这条 store 之间不存在相关。

最后，load/store 队列还必须完成消歧，即由 store 判断此前的推测是否合法。为此，每条 store 在提交之前检查 load 缓冲，看有没有比它年轻、访问同一物理地址、却已经抢在它前面推测执行的 load。如果有，就清除这些 load 并重放 [54]。

（2）TLB 层次与 Cache 层次。 load/store 队列与 TLB 的交互，只是一次访存全过程的第一步。下面详细介绍随后的几个步骤，它们涉及 TLB 与 L1 Cache 之间的交互。不失一般性，我们只讨论虚拟索引、物理 tag（VIPT）的 Cache，如图 L.16 所示，并以 x86-64 体系结构为例。64 位虚拟地址分成虚拟页号（VP）和页内偏移两部分。基本思路是让 TLB 查找与 L1 Cache 查找的一部分并行进行，以减小 TLB 访问延迟的影响。具体做法如图 L.16 所示：从虚拟页号中分出一部分作为 TLB 索引，选出所需的 TLB 组（步骤 a）；与此同时探查 L1 Cache，完成组的选择（同样是步骤 a）。VIPT 组织得当时，L1 Cache 选中组的各个 tag 准备好比较（步骤 c）之前，TLB 的 tag 匹配（步骤 b）就已经完成。

图 L.16　虚拟索引、物理 tag Cache 的操作。虚拟地址分成虚拟页号 VP 和页内偏移两部分。虚拟页号又分成 TLB 索引和 TLB tag，页内偏移则容纳块内偏移和（一部分）Cache 索引位。TLB 查找与 Cache 组的确定并行进行。图中是 L1 TLB 命中的例子，这时 L1 Cache 查找很快完成。这里的 L1 Cache 假定每组两路，每一组是 L1 Cache 中的一个水平切片。图内标注：VA (64 bits) = VP (52 bits) || Page Offset (12 bits)，虚拟地址（64 位）= 虚拟页号（52 位）‖ 页内偏移（12 位）；TLB tag || TLB index，TLB tag ‖ TLB 索引；Index || Block Offset，索引 ‖ 块内偏移；Way 0、Way 1，第 0 路、第 1 路；Tag、Data，tag、数据；Rest of the MMU and memory hierarchy，MMU 的其余部分和存储层次。

前面一直假定 L1 TLB 查找命中。图 L.17 是 L1 TLB 查找失效的情形。这时先在 L1 TLB 的失效状态处理寄存器（MSHR）中分配一项，记下这次访存的虚拟地址（步骤 c）。接着中止 Cache 访问（步骤 d），把 Cache 端口腾给其他指令；这些指令与这次 TLB 失效无关，可以继续执行，不必因为结构冒险而受阻。再假定所需的转换在 L2 TLB 中找到，就把它填入 L1 TLB（步骤 e），然后由 CPU 重放这条访存指令（步骤 f）。重放时重新开始 Cache 和 TLB 的组查找（步骤 g）和 TLB 的 tag 匹配（步骤 h）。这一次 L1 TLB 中有这个转换，Cache 的 tag 匹配就可以进行了（步骤 i）。

图 L.17　设置与图 L.16 相同，只是 L1 TLB 起初失效。这时中止 L1 Cache 查找，把它的端口腾给与这次 TLB 失效无关的其他指令。接着查找 L2 TLB。如果在 L2 TLB 中找到转换，就把它填入 L1 TLB，并重放起初 TLB 失效的那次访存。这一次 Cache 查找就能完成。图内标注同图 L.16。

上面描述的只是 TLB 与 L1 Cache 接口的一种可能的实现。这一设计还有两点微妙之处。

一是 VIPT 方法有一个前提：选择 Cache 索引所用的位，在物理地址空间和虚拟地址空间中必须保证相同。x86-64 体系结构中只有最低 12 位保证相同，因为它们对应最小的 4 KB 页。x86-64 体系结构也支持 2 MB 和 1 GB 的页，因此有人可能会想到从虚拟地址的最低 21 位和 30 位中取 Cache 索引位。但是，页的大小要等 TLB 查找之后才知道，所以选择 Cache 索引只能用最低 12 位。

二是 Cache 索引位只能从虚拟地址的最低 12 位中取，VIPT L1 Cache 的组数因此有上限。在 Cache 块为 64 字节的 x86-64 体系结构中，留给 Cache 索引的最多只有 6 位，即最多 64 个组。组数达到 64 以后，要扩大 L1 VIPT Cache，只能增加每组的路数，而不能增加组数。这样做可能带来功耗和访问时间方面的问题，页着色之类的技术可以部分缓解这些问题 [24, 50, 62, 80, 95]。

（3）页表遍历器与 MMU Cache、Cache 层次。 在前面图 L.17 的例子中，我们假定 L1 TLB 查找失效，因而中止了 VIPT Cache 访问，然后又假定 L2 TLB 命中。但 L2 TLB 查找也可能失效。这时要为 L2 TLB 分配一个 MSHR 项。这个 MSHR 就是图 L.8 中的 PTW 缓冲，记录所有已经启动的页表遍历。VIPT Cache 访问在 L1 TLB 失效时就已经中止，所以 L1 Cache 这一侧不必再做什么。

硬件 PTW 要与 MMU Cache 和处理器的数据 Cache 交互。在 x86-64 体系结构中，最好的情况是前三级页表的查找都命中，只有叶级页表项的访问要去查找数据 Cache 和主存。处理器把页表当作数据看待，所以指令地址转换产生的访问也送往数据 Cache，而不是指令 Cache。

图 L.18 给出了页表遍历的各个步骤，这里假定 MMU Cache 采用页遍历 Cache。设 CPU 启动了硬件 PTW，由 PTW 负责生成 L4～L1 各级页表中页表项的物理地址。对 L4～L2 的每一级，PTW 先探查 MMU Cache，看这一级的页表项能否很快找到。如果所需的页表项不在页遍历 Cache 中，就发生失效，这时用这一级页表项的物理地址去探查由数据 Cache 和主存组成的存储层次。找到页表项以后，把它填入 MMU Cache；这一步与下一级页表的地址生成并行进行，所以图 L.18 的状态图中没有画出。叶级页表项不会放在页遍历 Cache 中，因此 PTW 生成叶级页表项的物理地址以后，直接用它探查存储层次。在数据 Cache 或主存中找到这一项后，把它填入 TLB。最后，CPU 重放这次访存，再次对 L1 Cache 和 TLB 层次做 VIPT 查找。

图 L.18　采用页遍历 Cache 时，L2 TLB 失效之后页表遍历的各个步骤。PTW 生成 L4～L2 各级页表的物理地址，用它们查找页遍历 Cache。查找可能命中，也可能失效。失效时，到由数据 Cache 和主存组成的存储层次中找出这一级页表的页表项。最后，L1 级页表的查找直接送往存储层次。之后是 TLB 填充和访存重放。图内标注：L2 TLB Miss，L2 TLB 失效；PTW generates PA for L4（L3、L2、L1）lookup，PTW 生成查找 L4（L3、L2、L1）所用的物理地址；Lookup Page Walk $，查找页遍历 Cache；Lookup mem. hier.，查找存储层次；Found in D$ or memory，在数据 Cache 或内存中找到；Hit，命中；Miss，失效；TLB fill，TLB 填充；Memory replay，访存重放。

（4）故障。 在图 L.18 的情形中，所需的转换找到了，并按需要填入了地址转换硬件。但有些情况需要操作系统介入，转换不能立即填入。这几类情况统称为故障（fault）。

第一类故障是存储保护问题，起因有很多。例如，恶意程序可能企图写另一个程序的代码段。存放代码的页标记为只读、只可执行；程序企图写代码页的某个部分时，就产生故障，通知操作系统发生了保护违例，操作系统随后可以采取多种措施处理。又如，借助存储保护机制可以实现写时复制（copy-on-write）之类的技术，现代操作系统在 fork 等系统调用中为子进程创建地址空间时就用到写时复制；也可以实现内存去重，即把内容相同的多个物理页帧副本换成同一个物理页的单一实例 [33, 68, 77, 86]。

以页去重为例。设两个虚拟页映射到两个不同的物理页帧，而这两个页帧的数据完全相同。操作系统运行的软件发现了这一冗余，决定节省内存。于是操作系统修改页表，让两个虚拟页映射到同一个物理页，并对两个页都加上写保护，即两个页都没有写权限。同时，操作系统另用一个数据结构（例如 Linux 中的虚拟内存区域树 [27]）记下：共享这个物理页的各个虚拟页其实是可写的，只是写操作进行之前，必须先把物理页的内容复制到新的位置。

现在，设 CPU 上的程序对这个有写保护的页发出一条 store 指令。所需的转换或者在 TLB 中，或者由硬件 PTW 找到。无论哪种情况，store 指令都没有权限修改有写保护的页，于是发生保护故障，CPU 转去执行操作系统的保护故障处理程序。处理程序查看虚拟内存区域，发现目标页有写保护是因为它处在写时复制过程中，于是依次完成以下操作：在另一个物理页帧位置建立这个物理页帧的副本；更新页表，让引起故障的 store 指令所在的虚拟页改为指向这个副本；把这个页标记为可写；切换回用户进程的上下文。这时重放 store 指令。store 指令现在有了相应的写权限，就能继续执行，不再产生故障。

虚拟页还没有分配物理页帧时，也会产生故障。这类故障分两种：次要缺页（minor page fault，又称软缺页）和主要缺页（major page fault，又称硬缺页）。

CPU 访问某个页中的数据时，如果这个页已经在内存中，只是页表中没有标记为已分配，就发生次要缺页。这时，操作系统的缺页处理程序只需更新页表，记下这个页已经装入内存、不必从外存读入即可。次要缺页的起因有很多，例如：

  • 用户运行网页浏览器时，存放浏览器可执行代码的内存页可以由多个用户共享。第二个用户启动同一个浏览器时，就会产生次要缺页：二进制代码不从外存重新装入，而是把代码所在的物理页帧分配给新用户的虚拟页。
  • malloc 之类的内存分配调用。程序调用 malloc 请求分配多个页时，通常只是预留一段连续的虚拟页；物理页帧要等到每个虚拟页第一次被访问时才分配。这些首次访问引起次要缺页，由操作系统的缺页处理程序相应地更新页表 [64, 66]。
  • 有些页可能已经从进程的工作集中移出，但还没有写回磁盘或被擦除。例如，HP 的 OpenVMS 会把不必写回磁盘的页（自上次从磁盘读入以来没有修改过）移出，放进空闲链表。这些页要等到物理页帧重新分配时才会被覆盖，所以在分配出去之前，原来的进程如果又访问它，它仍然可用。这类故障不涉及磁盘延迟，因此只算次要缺页。

程序访问其映像中仍在外存的部分时，就发生主要缺页，这时必须把这个页装入内存。操作系统的缺页处理程序要找一个位置，可以是内存中空闲的物理页帧，也可以是非空闲的物理页帧。非空闲的页帧可能正被另一个进程使用，这时操作系统把其中的数据写出（如果是脏页），并在页表中撤销对这个页的标记。这样就腾出了空间，操作系统可以把所需的数据从外存读入这个位置。主要缺页的开销比次要缺页大，被中断程序的执行时间要加上一次外存访问延迟。

（5）访存重放。 TLB 失效（以及可能发生的缺页）处理完以后，需要重放当初 TLB 失效的那条指令。这里分两种情形：

  • TLB 失效之后。 设当初的 TLB 失效由一次页表遍历处理，没有发生缺页。这种情形如图 L.18 所示，缺少的转换已经填入 TLB，所以重放这次访存时 L1 TLB 命中，VIPT Cache 访问可以继续进行。（注意，VIPT Cache 访问不一定命中，因为这个 Cache 行可能还在存储层次中更低的一级。）也就是说，重放本身不会再产生地址转换开销。
  • 缺页之后。 设当初的 TLB 失效由一次页表遍历处理，但这次遍历引起了缺页。缺页处理程序执行完并采取相应措施以后，就有一个问题：当初那次访存的转换是否填入 TLB？这一转换必须先由操作系统更新，才能填入 TLB，因此大多数微结构不允许页表遍历器直接把它填入 TLB。这样，访存重放时还会发生第二次 TLB 失效，再启动一次页表遍历。不过，这通常不构成性能问题。这一转换刚由操作系统更新过，很可能就在较快的（L1/L2）处理器 Cache 中，能够很快取得，所以重放所做的页表遍历一般很快。

访存重放是否发生 TLB 失效固然重要，但我们还要再考虑另一个问题：没有发生缺页时，重放时的 Cache 访问是命中还是失效？为了弄清这一点，来看图 L.19。图中按照四级 x86-64 体系结构的基数树页表布局，画出了一个进程的地址空间。页表所指向的数据实际上相当于这个页表的第五级（Data），这一级的项数取决于具体的页大小和 Cache 行大小。图 L.19 采用 64 字节的 Cache 行，同时给出了 4 KB 页和 2 MB 页的例子：4 KB 页由 64 个 64 字节的 Cache 行组成，2 MB 页则由 32 768 个 64 字节的 Cache 行组成。

图 L.19　进程地址空间概貌，表示 x86-64 体系结构中页表与页表所指向的数据之间的关系。页表照常假定为四级，而数据相当于在 L1 级页表之下再加一级，由 L1 级页表指向。图中给出两种情形：Cache 行为 64 字节时，一个 4 KB 页含 64 个 Cache 行；另一个 2 MB 页含 32 768 个 Cache 行。图内标注：L4（L3、L2、L1）Page Table，第 4（3、2、1）级页表；L4 PTE 0 等，第 4 级页表项 0 等；Data，数据；$ Line 0 等，Cache 行 0 等。

图 L.19 说明了各级页表的局部性与它们所指向的数据的局部性之间的关系。一般来说，每次访存都要遍历这棵树：先做转换（前四级），再访问数据（叶级）。从根向叶逐级遍历，访问的局部性逐级降低，因为越往叶的方向走，每一级中一个表项所指向的内存粒度越小。换句话说，图中 4 KB 页里任何一个数据 Cache 行被访问过，L1 PTE 0 都必定被访问过，所以 L1 PTE 0 的访问局部性更高。这一局部性特点对 TLB 失效后的访存重放有重要影响：一次访存在 TLB 中失效，通常也就意味着重放之后访问的数据是冷的，因而还会发生 Cache 失效。

图 L.20 举例说明了页表与其所指向的数据在访问局部性上的关系。假定页表遍历需要到主存（DRAM）中查找所需的页表项。TLB 失效远没有数据访问频繁，所以所需的页表项很可能不在 DRAM 中某个已打开的行缓冲里。于是先发生行缓冲失效，接着查找 DRAM 阵列，找到转换（V→P），再把它填入各级 Cache 和 TLB，随后开始重放。但是，页表项的局部性已经差到需要查找 DRAM 阵列，这个转换所指向的物理页帧中，任何一个 Cache 行里的数据（通常）局部性还要更差，同样需要查找 DRAM 阵列。

图 L.20　页表遍历和重放的时序细节。这个例子假定页表遍历需要查找主存（DRAM），并假定 DRAM 中行缓冲失效，需要查找 DRAM 阵列。各级 Cache 和 TLB 填好以后，开始重放。页表所指向的数据，访问局部性比页表本身还差，所以重放也需要查找 DRAM（同样在行缓冲中失效）。图内标注：Lookup，查找；TLB miss，TLB 失效；Miss，失效；L1$，L1 Cache；LLC，末级 Cache；DRAM row buffer，DRAM 行缓冲；DRAM arrays，DRAM 阵列；V → P found，找到 V→P 转换；Fill，填充；Replay，重放；L1$ miss，L1 Cache 失效；Data found，找到数据。

「页表项所指向的数据，访问局部性比页表项本身低」这一准则有一个例外，偶尔出现在虚拟地址同义词的情形，即两个不同的虚拟页映射到同一个物理页帧。这时，即使一个同义虚拟页的转换是冷的，通过另一个虚拟地址对物理数据的访问也可能让数据留在 Cache 层次中较高的几级。于是，访问这个同义虚拟页时可能发生 TLB 失效，页表遍历的访存要深入存储层次的低层，而重放却能较快地找到所需的数据。
