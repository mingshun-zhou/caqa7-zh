计算机体系结构：量化研究方法

3.14 谬误与陷阱

下面几条谬误想说明的是：性能和能效很难预测，也不能从时钟频率、CPI 这样的单一指标推算出来。我们还将看到，在不同的基准测试程序上，不同的体系结构方法表现可能截然不同。

谬误　只要工艺不变，同一指令系统结构的两个不同版本在性能和能效上的表现很容易预测。

2008 年，Intel 推出了两款处理器。一款是面向低端上网本和个人移动设备（PMD）市场的 Atom 230，它同时实现了 x86 体系结构的 64 位和 32 位版本。Atom 是静态调度的双发射超标量处理器，微结构与 Arm A8 十分相似；A8 是单核处理器，是 A53 的前身。另一款是 Core i7 920，基于 OOO 的 Nehalem 微结构。而且，Atom 230 和 Core i7 920 是用同一种 45 nm Intel 工艺制造的。图 3.42 概括了 Intel Core i7 920、Arm Cortex-A8 和 Intel Atom 230 的特点。指令系统相同，底层制造工艺也相同，这就提供了一个难得的机会，可以直接比较两种截然不同的微结构。比较之前，先进一步介绍一下 Atom 230。

图 3.42　四核 Intel i7 920、一款典型的 Arm A8 处理器芯片（256 MiB L2、32 KiB L1，无浮点）和 Intel Atom 230 的概况。对比可以清楚地看出，面向 PMD（Arm）或上网本（Atom）的处理器，与面向服务器和高端台式机的处理器，设计理念截然不同。注意 i7 有 4 个核，每个核的性能都高于单核的 A8 或 Atom。这几款处理器都采用相当的 45 nm 工艺。

Atom 230 的微结构。 Atom 处理器用标准办法实现 x86 体系结构：把 x86 指令翻译成类似 RISC 的微操作。20 世纪 90 年代中期以来，所有 x86 实现都是这样做的。Atom 的微操作功能稍强一些，允许一个算术操作与一个 load 或 store 配对；后来的 OOO 微结构通过宏融合（macrofusion）也有了这种能力。有了这项优化，在典型的指令组合中，平均只有 4% 的指令需要一个以上的微操作。微操作在一条 16 级流水线中执行，和 Arm A8 一样，每个时钟周期按序发射两条指令。Atom 有两个整数 ALU，浮点加法和其他浮点操作各有一条流水线，另有两条访存流水线。因此，Atom 的双路执行比 Arm A8 更通用，但仍受按序发射的限制。Atom 230 有 32 KiB 指令 Cache 和 24 KiB 数据 Cache，二者共用同一晶片上 512 KiB 的 L2。Atom 230 还支持双线程的多线程，但这里只比较单线程的情况。

i7 和 Atom 230 工艺相同、指令系统也相同，我们也许会以为，二者的相对性能和能耗是可以预测的，也就是说，功耗和性能会接近线性地按比例变化。我们用三组基准测试程序来检验这一假设：

  • 第一组是单线程的 Java 基准测试程序，取自 DaCapo 和 SPEC JVM98 两个基准测试程序集（这些程序和测量方法见 Esmaeilzadeh 等（2011）的讨论）；
  • 第二组和第三组取自 SPEC CPU2006，分别是其中的整数程序和浮点程序。

从图 3.43 可以看出，i7 的性能远高于 Atom。在 i7 上，所有基准测试程序的速度都至少是 Atom 的 4 倍，两个 SPECFP 程序超过 10 倍，一个 SPECINT 程序超过 8 倍。两种处理器的时钟频率之比是 1.6，因此 i7 920 的优势主要来自低得多的 CPI：Atom 的 CPI，在 Java 程序上是 i7 920 的 2.8 倍，在 SPECINT 程序上是 3.1 倍，在 SPECFP 程序上是 4.3 倍。

图 3.43　一组单线程基准测试程序上的相对性能和能效。i7 920 的速度是 Atom 230 的 4 倍到 10 倍以上，但平均而言，能效只有 Atom 230 的约 1/2。柱形是 i7 相对于 Atom 的性能，即执行时间（i7）/执行时间（Atom）；折线是能耗，即能耗（Atom）/能耗（i7）。i7 的能效从未超过 Atom，只在 4 个基准测试程序上与 Atom 基本相当，其中 3 个是浮点程序。数据由 Esmaeilzadeh 等（2011）收集。SPEC 程序用标准的 Intel 编译器优化编译，Java 程序运行在 Sun（Oracle）Hotspot Java 虚拟机上。i7 上只有一个核工作，其余核处于深度节能模式。i7 打开了 Turbo Boost，性能优势因此扩大，但相对能效略有下降。图中 Speedup 为加速比，Energy efficiency 为能效，纵轴为 i7 920 与 Atom 230 的性能比和能耗比

然而，i7 920 的平均功耗略低于 43 W，Atom 的平均功耗只有 4.2 W，约为前者的 1/10。把性能和功耗合起来看，Atom 的能效通常是 i7 的 1.5 倍以上，常常达到 2 倍。两种处理器的底层工艺相同，这一比较清楚地表明：激进的超标量处理器靠动态调度和推测执行取得了性能优势，代价是能效上的明显劣势。

谬误　CPI 较低的处理器总是更快。

谬误　时钟频率较高的处理器总是更快。

关键在于，决定性能的是 CPI 与时钟频率的乘积。处理器靠深度流水线提高了时钟频率，还必须保持较低的 CPI，才能充分发挥高时钟频率的好处。同样，时钟频率高而 CPI 低的简单处理器，也可能更慢。

上一条谬误已经表明，即使指令系统相同，为不同环境设计的处理器，性能和能效也可能相差很远。实际上，即便是同一家公司同一系列的处理器，而且都面向高端应用，性能也可能相差很大。图 3.44 给出了 Intel 的两种 x86 实现的整数和浮点性能，以及 Intel 的一种 Itanium 体系结构实现的性能。

图 3.44　三种 Intel 处理器差别很大。Itanium 处理器有 2 个核，i7 有 4 个核，但基准测试只用了一个核。功耗一列是热设计功耗；对多核处理器，给出的是只有一个核工作时的估计值。

Pentium 4 是 Intel 造过的流水线设计最激进的处理器：流水线超过 20 级，有 7 个功能部件，Cache 中存放的是微操作而不是 x86 指令。实现如此激进，性能却相对较差，这清楚地说明，开发更多 ILP 的尝试（在途指令很容易达到 50 条）已经失败。Pentium 4 的功耗与 i7 相近，晶体管却比 i7 少，因为它的一级 Cache 只有 i7 的一半大，二级 Cache 只有 2 MiB，也没有三级 Cache。

Intel Itanium 是 VLIW 风格的体系结构。与动态调度的超标量处理器相比，它有可能降低复杂度，但时钟频率始终没能达到与主流 x86 处理器竞争的水平（不过它的总体 CPI 看来与 i7 相近）。分析这些结果时要注意，它们采用的实现工艺不同：流水线深度相当时，i7 的晶体管更快，时钟频率也就更高。尽管如此，性能差距之大仍然惊人，i7 的性能是 Pentium 的 3 倍以上。这一优势有相当一部分从何而来，下一条陷阱将给出解释。

陷阱　有时更大、更笨的反而更好。

21 世纪初，人们的注意力大多放在设计激进的处理器来开发 ILP 上，其中包括 Pentium 4 体系结构和 Intel Itanium：前者的流水线是微处理器中前所未有的最深流水线，后者的每时钟周期峰值发射率也是前所未有的最高水平。人们很快就发现，开发 ILP 的主要限制往往在存储系统。一级 Cache 失效的开销是 10～15 个周期，推测执行的 OOO 流水线能把其中相当大的一部分隐藏起来；末级 Cache（LLC，Last-Level Cache）失效则要访问主存，开销很可能达到 50～100 个时钟周期，OOO 流水线能隐藏的就很少了。

结果，这些设计尽管晶体管很多，技术也极其复杂巧妙，指令吞吐率却始终远未达到峰值。另一个变化也印证了这条陷阱：设计者不再试图用 ILP 隐藏更多的访存延迟，而是干脆把晶体管用来做大得多的 Cache。Pentium 4 是两级 Cache，Itanium 2 和 i7 都是三级 Cache；Itanium 2 和 i7 的三级 Cache 分别是 9 MiB 和 8 MiB，而 Pentium 4 的二级 Cache 只有 2 MiB。显然，做大 Cache 比设计 20 多级的 Pentium 4 流水线容易得多，而且从图 3.44 的数据来看，效果似乎也更好。

陷阱　有时聪明的又比更大、更笨的好。

过去十年里，转移预测领域出现了一个比较出人意料的结果：带 tag的混合预测器问世后，人们发现，在位数相同的条件下，较复杂的预测器能够胜过简单的 gshare 预测器（见图 3.10）。说它出人意料，一个原因是带 tag 的预测器还要拿出一部分位来存 tag，实际存储的预测反而更少，而 gshare 只有一个大的预测数组。尽管如此，不再把一条转移的预测误用到另一条转移上，由此得到的好处看来超过了把位分给 tag 而不分给预测所付出的代价。

陷阱　认为只要有合适的技术，就能获得大量可用的 ILP。

开发大量 ILP 的尝试之所以失败，原因有好几个。其中最重要的一个起初有些设计者并不接受：在结构常规的程序中，即使采用推测执行，也很难找到大量的 ILP。David Wall 1993 年的一项著名研究（见 Wall，1993）分析了在各种理想化条件下可用的 ILP 有多少。下面概述他针对一种处理器配置得到的结果，这种配置的能力大约是 2023 年最先进处理器的 4 到 8 倍。Wall 的研究详细记录了多种不同的方法，对开发 ILP 这一难题感兴趣的读者应当读一读研究全文。

这种激进的处理器有以下特点：

  1. 每个时钟周期最多发射和分派 64 条指令，没有任何发射限制。这一发射宽度是 2023 年最宽的处理器 IBM Power10 总发射宽度的 8 倍，每个时钟周期允许的 load 和 store 数最多是后者的 32 倍。前面讨论过，发射率很高时，复杂度和功耗都会成为严重的问题。
  2. 采用 1K 项的竞争预测器和 16 项的函数返回预测器。这一预测器与 2016 年最好的预测器相当，不是主要瓶颈。误预测在一个周期内处理完毕，但仍会限制推测执行的能力。
  3. 动态地对访存引用完美消歧。这一要求很激进，但窗口较小时或许能够做到。
  4. 寄存器重命名另有 64 个整数寄存器和 64 个浮点寄存器，比 2011 年最激进的处理器稍少。但这项研究假设所有指令的延迟都只有一个周期，而在 Golden Cove 这类处理器上，常见指令的延迟是 1～4 个周期，复杂指令最多可达 15 个周期。因此，有效的重命名寄存器数大约是这两种处理器的 5 倍。

图 3.45 给出了窗口大小变化时这种配置的结果。这种配置比现有的实现更复杂、更昂贵，在指令发射数上尤其如此；尽管如此，它为未来的实现可能达到的水平给出了一个有用的上限。这些数据很可能过于乐观，还有另一个原因：64 条指令之间没有任何发射限制，例如可以全是访存引用。近期内，谁都不会考虑让处理器具备这种能力。另外要记住，这些结果没有考虑 Cache 失效和非单周期延迟，而这两个因素的影响都很大。

图 3.45　每个时钟周期最多可任意发射 64 条指令时，多个整数和浮点程序可用的并行性与窗口大小的关系。重命名寄存器数虽然少于窗口大小，但所有操作的延迟都是 1 个周期，重命名寄存器数又等于发射宽度，因此处理器能够开发整个窗口内的并行性。图中 Window size 为窗口大小，Infinite 为无限，Benchmarks 为基准测试程序，Instruction issues per cycle 为每周期发射的指令数

图 3.45 中最令人吃惊的现象是：在上述切合实际的处理器约束下，窗口大小对整数程序的影响不像对浮点程序那样严重。这一结果反映了两类程序的关键区别。有两个浮点程序存在循环级并行，可开发的 ILP 因而较多；整数程序则不同，转移预测、寄存器重命名，以及程序本身的并行性就比较少，这些因素都是重要的限制。这一点至关重要，因为过去十年市场增长的大部分，如事务处理、Web 服务器等，依赖的是整数性能，而不是浮点性能。

Wall 的研究当时有人不相信，但 10 年以后，人们终于认清了现实：投入大量硬件资源只换来有限的性能提高，错误的推测执行又带来严重的能耗问题，两方面合在一起，迫使设计方向发生了转变。我们在结束语中还会回到这一话题。
