地址离开处理器后，首先遇到存储层次的最高一级，也就是第一级，这一级称为 Cache。由于局部性原理在许多层次上都成立，利用局部性提高性能的做法也很普遍，现在凡是用缓冲来重复使用常用对象的地方，都称为 Cache，例如文件 Cache、名字 Cache 等。

处理器在 Cache 中找到了所要的数据项，称为 Cache 命中；没有找到，就发生 Cache 失效。这时要从主存取出包含所请求字的一组数据，放进 Cache。这组数据大小固定，称为块，也称为行。根据时间局部性，这个字在不久的将来很可能还要用到，因此值得把它放在能快速访问的 Cache 里。根据空间局部性，块中的其他数据也很可能马上就要用到。

处理一次 Cache 失效所需的时间，既取决于存储器的延迟，也取决于它的带宽：延迟决定取出块中第一个字的时间，带宽决定取出块中其余部分的时间。Cache 失效由硬件处理。按序执行的处理器遇到失效会暂停（即停顿），直到数据到达为止。乱序执行的处理器中，使用这一结果的指令仍然要等，但其他指令在失效期间可以继续执行。

同样，程序访问的对象也不必全都放在主存里。虚拟存储就是允许一部分对象放在磁盘上。地址空间通常划分成固定大小的块，称为页。任何时刻，每一页要么在主存中，要么在磁盘上。处理器访问某一页中的数据项时，如果这一页既不在 Cache 中也不在主存中，就发生缺页，整个页要从磁盘调入主存。缺页的处理时间很长，因此由软件处理，处理器不停顿，在访问磁盘期间通常切换去执行别的任务。从宏观上看，Cache 与主存的关系和主存与磁盘的关系很相似：两者都依赖访问的局部性，容量和每位相对成本的对比关系也类似。

Cache 性能回顾

由于局部性，加上容量小的存储器速度快，存储层次能够大幅提高性能。评价 Cache 性能的一种方法，是扩展第 1 章的处理器执行时间公式，把处理器等待访存而停顿的周期数也计算在内，这部分周期称为访存停顿周期。于是，性能就等于时钟周期时间乘以处理器周期数与访存停顿周期数之和：

\[ \text{CPU 执行时间} = (\text{CPU 时钟周期数} + \text{访存停顿周期数}) \times \text{时钟周期时间} \]

这个公式假定 CPU 时钟周期数中已经包括处理 Cache 命中的时间，并且处理器在 Cache 失效期间停顿。B.2 节会重新审视这一简化假设。

访存停顿周期数取决于失效次数和每次失效的代价，后者称为失效开销：

\[ \begin{aligned} \text{访存停顿周期数} &= \text{失效次数} \times \text{失效开销} \\ &= \text{IC} \times \frac{\text{失效次数}}{\text{指令数}} \times \text{失效开销} \\ &= \text{IC} \times \frac{\text{访存次数}}{\text{指令数}} \times \text{失效率} \times \text{失效开销} \end{aligned} \]

最后一种写法的好处是各项都容易测量。指令数（IC）怎么测量，我们已经知道了；对推测执行的处理器，只计入提交的指令。每条指令的访存次数也可以用同样的办法测量：每条指令都需要一次取指访问，是否还需要数据访问也很容易判断。

注意，失效开销是按平均值计算的，下面却把它当作常数使用。实际上，发生失效时，Cache 后面的存储器可能正忙于处理先前的访存请求或者刷新；在处理器、总线和存储器各自时钟之间的接口上，时钟周期数也会变化。因此要记住，用单个数值表示失效开销只是一种简化。

失效率就是 Cache 访问中失效所占的比例，即失效的访问次数除以访问总次数。失效率可以用 Cache 模拟器测量：模拟器读入指令访问和数据访问的地址踪迹，模拟 Cache 的行为，确定哪些访问命中、哪些失效，最后报告命中和失效的总数。如今许多微处理器提供了统计失效次数和访存次数的硬件，用它测量失效率要容易、快速得多。

上面的公式是近似的，因为读和写的失效率、失效开销往往不同。这时可以分别按读和写来定义访存停顿时钟周期数，用到的是每条指令的读、写次数，读、写的失效开销（以时钟周期计），以及读、写的失效率：

\[ \begin{aligned} \text{访存停顿时钟周期数} = {} & \text{IC} \times \text{每条指令的读次数} \times \text{读失效率} \times \text{读失效开销} \\ & + \text{IC} \times \text{每条指令的写次数} \times \text{写失效率} \times \text{写失效开销} \end{aligned} \]

通常我们把读和写合起来，求出读写的平均失效率和平均失效开销，从而把完整的公式简化为：

\[ \text{访存停顿时钟周期数} = \text{IC} \times \frac{\text{访存次数}}{\text{指令数}} \times \text{失效率} \times \text{失效开销} \]

失效率是 Cache 设计最重要的指标之一，但后面几节会看到，它并不是唯一的指标。

例题　假设某台计算机在所有访存都命中 Cache 时，每条指令的周期数（CPI）为 1.0。数据访问只有 load 和 store，两者合计占指令总数的 50%。如果失效开销为 50 个时钟周期，失效率为 1%，那么所有访问都命中 Cache 时，这台计算机的速度是现在的多少倍？

解答　先计算总是命中的计算机的性能：

\[ \begin{aligned} \text{CPU 执行时间} &= (\text{CPU 时钟周期数} + \text{访存停顿周期数}) \times \text{时钟周期} \\ &= (\text{IC} \times \text{CPI} + 0) \times \text{时钟周期} \\ &= \text{IC} \times 1.0 \times \text{时钟周期} \end{aligned} \]

再看采用实际 Cache 的计算机，先计算访存停顿周期数：

\[ \begin{aligned} \text{访存停顿周期数} &= \text{IC} \times \frac{\text{访存次数}}{\text{指令数}} \times \text{失效率} \times \text{失效开销} \\ &= \text{IC} \times (1 + 0.5) \times 0.01 \times 50 \\ &= \text{IC} \times 0.75 \end{aligned} \]

式中的 (1 + 0.5) 表示每条指令有 1 次指令访问和 0.5 次数据访问。于是总的执行时间为：

\[ \begin{aligned} \text{CPU 执行时间}_{\text{cache}} &= (\text{IC} \times 1.0 + \text{IC} \times 0.75) \times \text{时钟周期} \\ &= 1.75 \times \text{IC} \times \text{时钟周期} \end{aligned} \]

性能之比是执行时间之比的倒数：

\[ \frac{\text{CPU 执行时间}_{\text{cache}}}{\text{CPU 执行时间}} = \frac{1.75 \times \text{IC} \times \text{时钟周期}}{1.0 \times \text{IC} \times \text{时钟周期}} = 1.75 \]

因此，没有 Cache 失效的计算机，速度是有实际 Cache 的计算机的 1.75 倍。

有些设计者喜欢用每条指令失效数来衡量失效率，而不用每次访存的失效数。两者的关系是：

\[ \frac{\text{失效次数}}{\text{指令数}} = \frac{\text{失效率} \times \text{访存次数}}{\text{指令数}} = \text{失效率} \times \frac{\text{访存次数}}{\text{指令数}} \]

已知每条指令的平均访存次数时，后一个公式很有用：用它可以把失效率换算成每条指令失效数，也可以反过来换算。例如，可以把上一个例题中每次访存的失效率换算成每条指令失效数：

\[ \frac{\text{失效次数}}{\text{指令数}} = \text{失效率} \times \frac{\text{访存次数}}{\text{指令数}} = 0.02 \times (1.5) = 0.030 \]

每条指令失效数常常改用每千条指令失效数来表示，这样得到的是整数而不是小数。因此，上面的结果也可以写成每千条指令 30 次失效。

每条指令失效数的优点是与硬件实现无关。例如，推测执行的处理器取出的指令数大约是实际提交指令数的 2 倍，如果按每次访存而不是每条指令统计失效，就会人为地压低失效率。它的缺点是与体系结构有关，例如 80x86 和 RISC-V 每条指令的平均访存次数可能相差很大。因此，只研究一个计算机系列的体系结构设计者最喜欢用每条指令失效数；不过，各种 RISC 体系结构彼此相似，从其中一种得出的结论也有助于理解其他几种。

例题　为了说明两种失效率公式是等价的，我们把前面的例题重做一遍，这次假设每千条指令的失效数为 30。用指令数表示，访存停顿时间是多少？

解答　重新计算访存停顿周期数：

\[ \begin{aligned} \text{访存停顿周期数} &= \text{失效次数} \times \text{失效开销} \\ &= \text{IC} \times \frac{\text{失效次数}}{\text{指令数}} \times \text{失效开销} \\ &= \text{IC}/1000 \times \frac{\text{失效次数}}{\text{指令数} \times 1000} \times \text{失效开销} \\ &= \text{IC}/1000 \times 30 \times 25 \\ &= \text{IC}/1000 \times 750 \\ &= \text{IC} \times 0.75 \end{aligned} \]

得到的结果与前面的例题相同，说明两个公式是等价的。

存储层次的四个问题

下面通过回答存储层次第一级的四个常见问题，继续介绍 Cache：

  • 问题 1：块可以放在上一级的什么位置？（块的放置）
  • 问题 2：如果块在上一级中，怎样找到它？（块的标识）
  • 问题 3：失效时应当替换哪一块？（块的替换）
  • 问题 4：写操作时怎么办？（写策略）

回答这些问题，有助于理解存储层次各级存储器在设计上的不同权衡，因此对每个例子我们都要问这四个问题。

问题 1：块可以放在 Cache 的什么位置？

从图 B.2 可以看出，根据对块放置位置的限制，Cache 的组织方式分为三类：

图 B.2　本例的 Cache 有 8 个块帧，存储器有 32 个块。从左到右是 Cache 的三种方案。全相联时，下一级的第 12 块可以放进 Cache 8 个块帧中的任意一个。直接映射时，第 12 块只能放进 4 号块帧（12 模 8）。组相联兼有两者的特点，第 12 块可以放在第 0 组中的任意位置（12 模 4）。每组有两块，因此第 12 块既可以放在 Cache 的 0 号块，也可以放在 1 号块。实际的 Cache 有成千上万个块帧，实际的存储器有数以百万计的块。图中的组相联组织有 4 组，每组两块，称为两路组相联。假设 Cache 中原来什么都没有，要访问的块地址是下一级的第 12 块。图内标注：Fully associative: block 12 can go anywhere，全相联：第 12 块可以放在任意位置；Direct mapped: block 12 can go only into block 4 (12 MOD 8)，直接映射：第 12 块只能放进 4 号块（12 MOD 8）；Set associative: block 12 can go anywhere in set 0 (12 MOD 4)，组相联：第 12 块可以放在第 0 组中的任意位置（12 MOD 4）；Block no.，块号；Set，组；Block frame address，块帧地址；Cache，Cache；Memory，存储器。

  • 如果每个块在 Cache 中只能出现在唯一的位置，这种 Cache 称为直接映射。映射关系通常是

    \[ (\textit{块地址})\ \text{MOD}\ (\textit{Cache 中的块数}) \]

  • 如果块可以放在 Cache 中的任意位置，这种 Cache 称为全相联。

  • 如果块只能放在 Cache 中一组受限的位置上，这种 Cache 称为组相联。所谓组，就是 Cache 中的一组块。块先映射到某个组，然后可以放在该组内的任意位置。组通常用位选择的办法确定，即

    \[ (\textit{块地址})\ \text{MOD}\ (\textit{Cache 中的组数}) \]

    如果每组有 \(n\) 块，这种 Cache 放置方式称为 n 路组相联。

从直接映射到全相联，实际上是组相联度由低到高连续变化的一系列级别。直接映射就是一路组相联；有 \(m\) 块的全相联 Cache 可以称为「\(m\) 路组相联」。换一种说法，也可以把直接映射看成有 \(m\) 组，把全相联看成只有一组。

如今绝大多数处理器的 Cache 是直接映射、两路组相联或四路组相联，原因稍后就会看到。

问题 2：如果块在 Cache 中，怎样找到它？

Cache 的每个块帧都有一个地址 tag（标签），给出这一块的块地址。凡是可能含有所需信息的 Cache 块，都要检查它的 tag 是否与处理器给出的块地址相符。由于速度至关重要，通常所有可能的 tag 都并行查找。

还必须有办法判断某个 Cache 块中的信息是否有效。最常用的办法是给 tag 加一个有效位，表明这一项是否含有有效地址。有效位没有置位，这个地址就不可能匹配。

讨论下一个问题之前，先看看处理器地址与 Cache 的关系。图 B.3 给出了地址的划分方式。地址首先分成块地址和块内偏移两部分，块帧地址又可以进一步分成 tag 字段和索引字段。块内偏移字段从块中选出所需的数据，索引字段选出组，tag 字段则与组中的 tag 比较，以判断是否命中。比较时虽然也可以不只用 tag，而用地址中更多的位，但没有必要，原因如下：

图 B.3　组相联或直接映射 Cache 中地址的三个部分。tag 用来检查组中的所有块，索引用来选择组，块内偏移是所需数据在块内的地址。全相联 Cache 没有索引字段。图内标注：Block address，块地址；Tag，tag；Index，索引；Block offset，块内偏移。
  • 块内偏移不应参与比较。因为整个块要么都在、要么都不在，所以按定义，块内偏移取什么值都会匹配。
  • 检查索引是多余的。因为索引已经用来选出要检查的组了。例如，存放在第 0 组中的地址，索引字段必定为 0，否则就不可能存放在第 0 组；第 1 组中地址的索引值必定为 1；依此类推。这项优化减小了 Cache tag 存储器的宽度，从而节省硬件和功耗。

如果 Cache 总容量不变，提高相联度就会增加每组的块数，于是索引变短、tag 变长。也就是说，相联度越高，图 B.3 中 tag 与索引的分界线越往右移；到了全相联 Cache 这一端点，索引字段就没有了。

问题 3：Cache 失效时应当替换哪一块？

发生失效时，Cache 控制器必须选出一块，用所需的数据替换它。直接映射放置的一个好处是硬件决策变得简单，简单到根本不用选择：命中检查只查一个块帧，能替换的也只有这一块。采用全相联或组相联放置时，失效时有许多块可供选择。选择替换块的主要策略有三种：

  • 随机：为了让分配均匀，随机选择候选块。有些系统生成伪随机的块号，以得到可重现的行为，这在调试硬件时特别有用。
  • 最近最少使用（LRU）：为了降低丢弃即将用到的信息的概率，LRU 记录各块的访问情况，以过去预测未来，替换最长时间没有用过的那一块。LRU 依据的是局部性的一个推论：如果最近用过的块很可能还会再用，那么最近最少使用的块就是丢弃的好人选。
  • 先进先出（FIFO）：由于 LRU 计算起来可能比较复杂，FIFO 改为找出最老的块，以此近似 LRU。

随机替换的一个优点是硬件实现简单。需要跟踪的块数越多，LRU 的代价就越高，所以通常只能近似实现。一种常用的近似方案（常称为伪 LRU）为 Cache 的每组设置一组位，每一位对应 Cache 中的一路。所谓路，就是组相联 Cache 中的一个存储体，四路组相联 Cache 有四路。访问某一组时，把含有所需块的那一路对应的位置 1；如果该组的所有位都已置 1，就把除最近置 1 的那一位以外的位全部清零。必须替换一块时，处理器从对应位为 0 的路中选一块；可选的不止一块时，往往随机选择。这种方法之所以近似 LRU，是因为从组内所有块上一次全部访问过以来，被替换的块一直没有再访问过。图 B.4 给出了 LRU、随机和 FIFO 三种替换策略在失效率上的差别。

问题 4：写操作时怎么办？

处理器对 Cache 的访问以读为主。所有指令访问都是读，而且大多数指令不写存储器。附录 A 的图 A.32 和图 A.33 表明，RISC-V 程序中 store 约占 10%，load 约占 26%，因此写占全部访存流量的 10%/(100% + 26% + 10%)，约 7%；在数据 Cache 的流量中，写占 10%/(26% + 10%)，约 28%。按照加快常见情况的原则，Cache 应当针对读来优化，何况处理器历来要等读完成，却不必等写完成。但是 Amdahl 定律（1.9 节）提醒我们，高性能设计不能忽视写的速度。

好在常见情况也是容易加快的情况。读出并比较 tag 的同时，就可以从 Cache 中读出块，因此块地址一到，就可以开始读块。如果读命中，块中所请求的部分立即送给处理器；如果失效，读出的值没有用处，但除了在台式计算机和服务器中多一些功耗之外，也没有害处，丢弃读出的值即可。

写就不能这么乐观了。要等检查完 tag、确认地址命中以后，才能开始修改块。tag 检查不能与写同时进行，因此写通常比读慢。另一个复杂之处在于，处理器还要指明写的大小，通常在 1～8 字节之间，块中只有这一部分可以改动。相比之下，读多读一些字节也无妨。

不同的 Cache 设计，往往就区别在写策略上。写 Cache 时有两种基本选择：

  • 写直达（write through）：信息既写入 Cache 中的块，也写入下一级存储器中的块。
  • 写回（write back）：信息只写入 Cache 中的块。修改过的 Cache 块要等到被替换时才写回主存。

为了减少替换时写回块的次数，通常为每个块设一个状态位，称为脏位（dirty bit），用来指明这个块是脏的（在 Cache 中修改过）还是干净的（没有修改过）。干净的块在失效时不必写回，因为下一级存储器中的信息与 Cache 中的相同。

写回和写直达各有优点。

  • 写回的写操作以 Cache 的速度进行，对一个块的多次写也只需对下一级存储器写一次。由于有些写操作根本不会到达存储器，写回占用的存储带宽较少，因此在多处理器中很有吸引力。写回对存储层次其余部分和存储互连的使用也比写直达少，因而更省功耗，适合嵌入式应用。
  • 写直达比写回容易实现。Cache 中的块始终是干净的，因此读失效永远不会引起对下一级的写操作，这一点与写回不同。写直达的另一个优点是下一级存储器总保存着数据的最新副本，数据一致性因此容易处理。数据一致性对多处理器和 I/O 都很重要，第 5 章和附录 D 将讨论这一问题。有了多级 Cache，较高一级的 Cache 更适合采用写直达，因为写操作只需传到下一级，不必一直传到主存。

后面我们会看到，I/O 和多处理器对写策略的要求自相矛盾：为了减少访存流量，它们希望处理器的 Cache 采用写回；为了让 Cache 与存储层次的较低各级保持一致，它们又希望采用写直达。

采用写直达时，如果处理器必须等写操作完成，就称处理器发生了写停顿（write stall）。减少写停顿的常用办法是设置写缓冲：数据一写入缓冲，处理器就可以继续执行，于是处理器的执行与存储器的更新重叠进行。我们很快会看到，即使有写缓冲，写停顿也仍然可能发生。

写操作不需要读出数据，因此写失效时有两种选择：

  • 写分配（write allocate）：写失效时先在 Cache 中分配这个块，再执行前面所说的写命中操作。这种做法很自然，写失效的处理与读失效一样。
  • 不写分配（no-write allocate）：这种做法看起来有些反常。写失效不影响 Cache，块只在下一级存储器中修改。

因此，采用不写分配时，块要等到程序读它时才进入 Cache；采用写分配时，即使只写过、从未读过的块，也会留在 Cache 中。下面看一个例子。

例题　假设有一个采用写回的全相联 Cache，表项很多，开始时为空。下面是 5 次访存操作的序列（方括号中是地址）：

Write Mem[100];
Write Mem[100];
Read Mem[200];
Write Mem[200];
Write Mem[100].

分别采用不写分配和写分配时，命中和失效各有多少次？

解答　采用不写分配时，地址 100 不在 Cache 中，写操作也不分配块，因此前两次写都失效。地址 200 也不在 Cache 中，因此读操作也失效。接下来对地址 200 的写命中。最后对 100 的写仍然失效。所以不写分配的结果是 4 次失效、1 次命中。

采用写分配时，第一次访问 100 和第一次访问 200 失效，其余访问都命中，因为 100 和 200 都已经在 Cache 中。所以写分配的结果是 2 次失效、3 次命中。

两种写失效策略都可以与写直达或写回搭配使用。写回 Cache 通常采用写分配，希望以后对这个块的写都由 Cache 截住。写直达 Cache 则常采用不写分配，理由是：即使以后还有对这个块的写，这些写也还是要传到下一级存储器，分配了又有什么好处呢？

一个例子：Opteron 的数据 Cache

下面用一个实例把这些概念落到实处。图 B.5 给出了 AMD Opteron 微处理器中数据 Cache 的组成。这个 Cache 容纳 65 536（64 K）字节数据，块大小为 64 字节，采用两路组相联放置、LRU 替换和写回，写失效时采用写分配。

我们按照图 B.5 中标出的步骤，跟踪一次 Cache 命中的过程（4 个步骤用带圈的数字表示）。B.5 节会讲到，Opteron 把 48 位虚拟地址送给 Cache 作 tag 比较，同时把它转换成 40 位物理地址。

Opteron 没有用满 64 位虚拟地址，原因有两个：一是设计者认为目前还没有人需要那么大的虚拟地址空间；二是地址位数少一些，Opteron 的虚拟地址映射也简单一些。设计者计划在以后的微处理器中增加虚拟地址的位数。

进入 Cache 的物理地址分成两个字段：34 位的块地址和 6 位的块内偏移（\(64 = 2^6\)，\(34 + 6 = 40\)）。块地址再分成地址 tag 和 Cache 索引两部分。这一划分就是步骤 1。

Cache 索引用来选出要检查的 tag，以判断所需的块在不在 Cache 中。索引的位数取决于 Cache 容量、块大小和组相联度。Opteron Cache 的相联度为 2，索引按下式计算：

图 B.5　Opteron 微处理器中数据 Cache 的组成。这个 64 KiB 的 Cache 采用两路组相联，块大小为 64 字节。9 位索引从 512 个组中选出一组。图中用带圈的数字按发生的先后标出了读命中的 4 个步骤。块内偏移中的 3 位与索引合起来，作为 RAM 地址选出所需的 8 个字节。因此，Cache 的数据分成两部分，每部分有 4096 个 64 位字，各存放 512 个组的一半。从下一级存储器到 Cache 的连线在本例中没有用到，它用于失效时装入 Cache。离开处理器的地址是 40 位，因为它是物理地址而不是虚拟地址。图 B.24 说明了 Opteron 在访问 Cache 时怎样把虚拟地址映射为物理地址。图内标注：Block address，块地址；Block offset，块内偏移；Tag，tag；Index，索引；Valid，有效位；Data，数据；512 blocks，512 个块；CPU address，CPU 地址；Data in，数据输入；Data out，数据输出；2:1 mux，二选一多路选择器；Victim buffer，牺牲缓冲；Lower-level memory，下一级存储器。

\[ 2^{\text{索引}} = \frac{\text{Cache 容量}}{\text{块大小} \times \text{组相联度}} = \frac{65\,536}{64 \times 2} = 512 = 2^9 \]

所以索引有 9 位，tag 有 \(34 - 9 = 25\) 位。这 9 位索引已经能选出所需的块，但 64 字节远远多于处理器一次要用的数据。因此，把 Cache 的数据部分组织成 8 字节宽更为合理，8 字节正是 64 位 Opteron 处理器的自然数据字长。这样，除了用 9 位索引选出 Cache 块，还要用块内偏移中的另外 3 位选出所需的 8 个字节。索引选择就是图 B.5 中的步骤 2。

从 Cache 中读出两个 tag 后，把它们与处理器送来的块地址中的 tag 部分比较，这就是图中的步骤 3。为了保证 tag 中的信息有效，有效位必须置位，否则比较结果不予理会。

假设有一个 tag 匹配，最后一步就是通知处理器从 Cache 中装入正确的数据，数据取自二选一多路选择器中胜出的那一路输入。Opteron 为这 4 个步骤留出 2 个时钟周期，因此后面 2 个时钟周期内的指令如果要用这条 load 的结果，就必须等待。

和其他任何 Cache 一样，Opteron 处理写比处理读复杂。如果要写的字在 Cache 中，前 3 个步骤与读相同。但 Opteron 是乱序执行的，所以要等它发出指令已经提交的信号，并且 Cache tag 比较表明命中，才把数据写入 Cache。

到这里我们假定的都是 Cache 命中这种常见情况。失效时又会怎样呢？读失效时，Cache 向处理器发出信号，告诉它数据还没有准备好，同时从存储层次的下一级读出 64 字节。块的前 8 个字节延迟 7 个时钟周期送到，其余部分每 8 个字节需要 2 个时钟周期。数据 Cache 是组相联的，因此要选择替换哪个块。Opteron 采用 LRU，选出最久没有访问过的块，所以每次访问都要更新 LRU 位。替换一个块，就要更新数据、地址 tag、有效位和 LRU 位。

Opteron 采用写回，旧的数据块可能修改过，因此不能简单地丢掉。Opteron 为每个块设 1 个脏位，记录这个块是否写过。如果被替换的「牺牲者」（victim）修改过，它的数据和地址就送进牺牲缓冲（victim buffer）。（这种结构类似于其他计算机中的写缓冲。）Opteron 的牺牲缓冲可以存放 8 个牺牲块，它在 Cache 进行其他操作的同时，把牺牲块写到存储层次的下一级。牺牲缓冲满了，Cache 就必须等待。

Opteron 在读失效和写失效时都分配块，因此写失效的处理与读失效非常相似。

以上是数据 Cache 的工作过程。但数据 Cache 不能满足处理器的全部访存需求，处理器还需要指令。用一个 Cache 同时提供指令和数据也可以，但它可能成为瓶颈。例如，流水线处理器执行 load 或 store 指令时，会同时请求一个数据字和一个指令字。因此，只有一个 Cache 时，load 和 store 会引起结构冒险，导致停顿。解决这个问题的简单办法是把 Cache 一分为二：一个专门存放指令，另一个专门存放数据。最近的大多数处理器都采用分离的 Cache，Opteron 也是如此，它除了 64 KiB 的数据 Cache，还有一个 64 KiB 的指令 Cache。

处理器知道自己发出的是指令地址还是数据地址，因此两个 Cache 可以各设端口，存储层次与处理器之间的带宽于是提高到原来的 2 倍。分离的 Cache 还可以分别优化，采用不同的容量、块大小和相联度，可能得到更好的性能。（Opteron 的指令 Cache 和数据 Cache 各存一类信息；与之相对，既能存放指令也能存放数据的 Cache 称为统一（unified）Cache 或混合（mixed）Cache。）

图 B.6 表明，指令 Cache 的失效率比数据 Cache 低。指令和数据分开后，指令块与数据块之间的冲突失效消除了；但两类信息各自能用的 Cache 空间也随之固定。对失效率来说，哪一点更重要呢？公平的比较要求 Cache 总容量相同，例如 16 KiB 指令 Cache 加 16 KiB 数据 Cache，应该与 32 KiB 的统一 Cache 比较。要算出分离的指令 Cache 和数据 Cache 的平均失效率，还需要知道访存中分别有多大比例访问这两个 Cache。根据附录 A 的数据，指令访问占 \(100\%/(100\% + 26\% + 10\%)\)，约 74%；数据访问占 \((26\% + 10\%)/(100\% + 26\% + 10\%)\)，约 26%。我们很快会看到，分离 Cache 对性能的影响不只表现在失效率的变化上。
