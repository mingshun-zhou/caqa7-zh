计算机体系结构：量化研究方法

D.4 I/O 性能、可靠性度量和基准测试程序

I/O 性能有一些度量在设计中找不到对应物。一是多样性：哪些 I/O 设备可以连接到计算机系统上？二是容量：一个计算机系统可以连接多少台 I/O 设备？

图 D.8　响应时间和吞吐率的传统生产者-服务器模型。任务放进缓冲区时，响应时间开始计算；服务器完成任务时，响应时间结束。吞吐率是服务器在单位时间内完成的任务数。图内标注：Producer，生产者；Queue，队列；Server，服务器。

除了这些独有的度量，传统的性能度量，即响应时间和吞吐率，也适用于 I/O。（I/O 吞吐率有时称为 I/O 带宽，响应时间有时称为延迟。）下面两幅图说明响应时间和吞吐率怎样此消彼长。图 D.8 是简单的生产者-服务器模型：生产者产生要执行的任务，放进缓冲区；服务器从这个先进先出的缓冲区中取出任务并执行。

响应时间定义为一个任务从放进缓冲区到服务器完成它所经历的时间。吞吐率就是服务器在一段时间内平均完成的任务数。要得到尽可能高的吞吐率，服务器就不能空闲，因此缓冲区永远不能为空。但响应时间包括任务在缓冲区中等待的时间，缓冲区为空，响应时间才会缩短。

I/O 性能的另一项度量是 I/O 对处理器执行的干扰。传输数据可能干扰另一个进程的执行，处理 I/O 中断也有开销。这里我们关心的是：因为要为另一个进程做 I/O，一个进程的执行时间会延长多少。

吞吐率与响应时间

图 D.9 画出了一个典型 I/O 系统的吞吐率与响应时间（即延迟）的关系。在曲线的拐点区域，吞吐率稍微提高一点，响应时间就会长很多；反过来，响应时间稍微缩短一点，吞吐率就会低很多。

图 D.9　吞吐率与响应时间。延迟通常用响应时间来报告。注意，响应时间最短时，吞吐率只有最大值的 11%；而吞吐率达到 100% 时，响应时间是最短响应时间的 7 倍。还要注意，这条曲线的自变量是隐含的：要描出这条曲线，通常是改变负载（并发度）。这些数据是 Chen 等［1990］在一个磁盘阵列上收集的。图内标注：纵轴 Response time (latency) (ms)，响应时间（延迟）（ms）；横轴 Percentage of maximum throughput (bandwidth)，占最大吞吐率（带宽）的百分比。

这两个要求相互冲突，体系结构设计者怎样权衡呢？如果计算机要与人交互，图 D.10 给出了一个答案。人与计算机的一次交互称为一次事务，分成三部分：

  1. 输入时间：用户输入命令的时间。
  2. 系统响应时间：从用户输入命令到完整的响应显示出来之间的时间。
  3. 思考时间：从收到响应到用户开始输入下一条命令之间的时间。
图 D.10　传统系统和图形系统中，用户与交互式计算机的一次事务分成输入时间、系统响应时间和用户思考时间。输入时间与系统响应时间无关，两种响应时间下相同：传统系统为 4 秒，图形系统为 0.25 秒。缩短响应时间，事务时间实际减少的量比响应时间本身减少的量还多。（引自 Brady［1986］。）图内标注：Workload，工作负载；Conventional interactive workload (1.0 / 0.3 sec system response time)，传统交互式工作负载（系统响应时间 1.0 / 0.3 秒）；High-function graphics workload (1.0 / 0.3 sec system response time)，高功能图形工作负载（系统响应时间 1.0 / 0.3 秒）；−34% total (−70% think)，总时间减少 34%（思考时间减少 70%）；−70% total (−81% think)，总时间减少 70%（思考时间减少 81%）；Time (sec)，时间（秒）；Entry time，输入时间；System response time，系统响应时间；Think time，思考时间。

这三部分之和称为事务时间。有几项研究报告，用户的工作效率与事务时间成反比。图 D.10 的结果表明，系统响应时间缩短 0.7 秒，传统事务就能节省 4.9 秒（34%），图形事务能节省 2.0 秒（70%）。这个结果看似不可能，原因在于人的天性：响应越快，人需要的思考时间就越短。这项研究虽然已有 20 年，处理器也已经快到原来的 1000 倍，但响应时间常常仍远远超过 1 秒。例如，台式 PC 启动应用程序时要做许多次磁盘 I/O，点击 Web 链接时有网络延迟，都会造成很长的等待。

响应时间对用户工作效率很重要，因此 I/O 基准测试程序也考虑响应时间与吞吐率之间的权衡。图 D.11 列出了三个 I/O 基准测试程序的响应时间限制。它们报告的都是满足限制条件时的最大吞吐率，限制条件要么是 90% 的响应时间小于某个界限，要么是平均响应时间小于某个界限。

事务处理基准测试程序

事务处理（TP，也称联机事务处理 OLTP）主要关心 I/O 速率（每秒的磁盘访问次数），而不是数据速率（以每秒传输的数据字节数衡量）。TP 通常要从许多终端修改大量的共享信息，并且 TP 系统要保证出现失效时行为正确。例如，假设顾客在 ATM 上取钱时，银行的计算机发生了失效，TP 系统要保证：如果顾客拿到了钱，账户就扣款；而且，如果顾客没拿到钱，账户就保持不变。航空订票系统和银行一样，都是 TP 的传统用户。

第 1 章讲过，TP 界的二十几位人士联手为业界制定了一个基准测试程序。为了避免各自公司法务部门的追究，他们匿名发表了这份报告［Anon. et al. 1985］。这份报告促成了事务处理委员会（TPC）的成立，TPC 成立以来已经推出了八个基准测试程序。图 D.12 归纳了这些基准测试程序。

下面以 TPC-C 为例，让读者对这些基准测试程序有个大致的印象。TPC-C 用一个数据库模拟批发供应商的订单录入环境，包括录入和配送订单、记录付款、查询订单状态，以及监控各仓库的库存水平。它同时运行五种复杂程度不同的事务；数据库包括九张表，记录数和客户数都可以按比例扩展。TPC-C 的度量有两项：一是每分钟事务数（tpmC），二是系统价格，包括硬件、软件和三年的维护支持。第 1 章的图 1.17 介绍了 TPC-C 性能和性价比最高的系统。

TPC 基准测试程序最先具备下面这些不寻常的特点，有的特点至今仍只有它们具备：

  • 基准测试结果中包括价格。 提交的结果要包括硬件、软件和维护协议的费用，因此既可以按高性能来评价，也可以按性价比来评价。
  • 数据集的规模通常必须随吞吐率的提高而扩大。 这些基准测试程序力图模拟真实的系统，而在真实系统中，系统承受的需求和其中存储的数据量是一起增长的。例如，每分钟有成千上万人访问几百个银行账户，这是不合情理的。
  • 基准测试结果要经过审计。 结果提交之前，必须经过 TPC 认证的审计员批准。审计员执行 TPC 的规则，力求只让公正的结果提交上来。结果可以受到质疑，争议提交 TPC 裁决。
  • 性能度量是吞吐率，但响应时间受限。 例如，TPC-C 要求 90% 的新订单事务响应时间小于 5 秒。
  • 基准测试程序由一个独立的组织维护。 TPC 用收取的会费支付管理机构的开支，管理机构包括一个首席运营办公室。这个组织负责裁决争议、以通信投票的方式批准基准测试程序的修改、召开理事会会议，等等。

SPEC 系统级文件服务器、邮件和 Web 基准测试程序

SPEC 的基准测试工作以刻画处理器性能最为出名，但它也推出了文件服务器、邮件服务器和 Web 服务器的基准测试程序。

七家公司商定了一个合成基准测试程序，称为 SFS，用来评测运行 Sun Microsystems 网络文件服务（NFS）的系统。这个基准测试程序后来升级为 SFS 3.0（也称 SPEC SFS97_R1），改进有三点：一是支持 NFS 第 3 版；二是除 UDP 外也用 TCP 作传输协议；三是操作的组合更符合实际。SFS 中读、写和文件操作的合成组合来自对 NFS 系统的测量。SFS 还提供了用于比较性能的默认参数。例如，写操作一半以 8 KB 的整块进行，另一半以 1 KB、2 KB 或 4 KB 的部分块进行；读操作中，整块占 85%，部分块占 15%。

与 TPC-C 一样，SFS 也按报告的吞吐率扩大存储的数据量：每秒的 NFS 操作每增加 100 次，容量就必须增加 1 GB。SFS 还限制平均响应时间，限值为 40 ms。图 D.13 给出了两种 NetApp 系统的平均响应时间与吞吐率的关系。遗憾的是，SFS 不像 TPC 基准测试程序那样按不同的价格配置作归一化。

SPECMail 是用来帮助评测互联网服务提供商邮件服务器性能的基准测试程序。SPECMail2001 基于标准的互联网协议 SMTP 和 POP3，在用户数从 10,000 扩大到 1,000,000 的过程中测量吞吐率和用户响应时间。

SPECWeb 是评测万维网服务器性能的基准测试程序，度量的是同时进行的用户会话数。SPECWeb2005 的工作负载模拟对一家 Web 服务提供商的访问，该服务器为若干个机构提供主页。它有三种工作负载：银行（HTTPS）、电子商务（HTTP 和 HTTPS）和技术支持（HTTP）。

可信性基准测试的例子

TPC-C 基准测试程序其实有一项可信性要求：被测系统必须能够处理单块磁盘的失效。这实际上意味着，所有提交结果的厂商都在存储系统中采用了某种 RAID 组织。

图 D.13　NetApp FAS3050c NFS 服务器两种配置的 SPEC SFS97_R1 性能。两个处理器的配置达到每秒 34,089 次操作，四个处理器的配置达到每秒 47,927 次操作。这些结果发布于 2005 年 5 月，系统配置为：Data ONTAP 7.0.1R1 操作系统，2.8 GHz Pentium Xeon 微处理器，每个处理器 2 GB DRAM，每个系统 1 GB 非易失存储器，168 块 15 K RPM、72 GB 的光纤通道（Fibre Channel）磁盘。这些磁盘通过两个或四个 QLogic ISP-2322 FC 磁盘控制器连接。图内标注：Response time (ms)，响应时间（ms）；Operations/second，每秒操作数；2 Xeons / 4 Xeons，2 个 / 4 个 Xeon；4 Opterons / 8 Opterons，4 个 / 8 个 Opteron。

近年来的研究转向考察系统容错的实际效果。Brown 和 Patterson [2000] 提出了一种衡量可用性的方法：向系统中注入故障，观察系统服务质量指标随时间的变化。以 Web 服务器为例，最直接的指标有两个：一是性能，用每秒完成的请求数来衡量；二是容错能力，用存储子系统、网络连接拓扑等能够容忍的故障数来衡量。

最初的实验只注入一个故障（例如磁盘扇区写错误），然后通过服务质量指标记录系统的行为。实验比较了 Linux、Solaris 和 Windows 2000 Server 提供的软件 RAID 实现，用 SPECWeb99 产生负载并测量性能。为了注入故障，实验把软件 RAID 卷中的一块 SCSI 磁盘换成了一个模拟磁盘。这个模拟磁盘其实是一台 PC，它运行的软件通过一块 SCSI 控制器工作，在 SCSI 总线上的其他设备看来就是一块磁盘。借助这个磁盘模拟器，就可以向系统中注入故障。注入的故障既有各种瞬时磁盘故障，如可纠正的读错误；也有永久故障，如写操作时的磁盘介质失效。

图 D.14 给出了各个系统在不同故障下的行为，上面两幅图分别是 Linux（左）和 Solaris（右）。RAID 系统如果在重建完成之前又坏了第二块磁盘，就可能丢失数据，因此重建时间（MTTR）越长，可用性越低。但是，重建越快，应用程序的性能下降得越多，因为重建要占用正在运行的应用程序的 I/O 资源。因此，策略上只能二选一：要么在重建期间承受性能损失，要么延长易损窗口，从而降低预计的 MTTF。

图 D.14　在同一台计算机上分别运行 Red Hat 6.0 Linux、Solaris 7 和 Windows 2000 操作系统时，软件 RAID 系统的可用性基准测试。注意 Linux 与 Windows、Solaris 在重建速度上的设计理念不同。纵轴是运行 SPECWeb99 时以每秒命中数表示的系统行为。箭头表示注入故障的时刻。图上方的横线给出注入故障之前性能的 99% 置信区间。99% 置信区间的意思是：如果变量的值落在这个范围之外，出现这个值的概率只有 1%。图内标注：Hits per second，每秒命中数；Time (minutes)，时间（分钟）；Reconstruction，重建。

除了源代码，接受测试的系统都没有用文档说明自己的重建策略，但只注入一次故障，就足以看出这些策略的特点。实验发现，当一块工作中的磁盘因故障停用时，Linux 和 Solaris 都会自动在热备盘上重建 RAID 卷。Windows 虽然也支持 RAID 重建，但必须手动启动。因此，如果没有人工干预，Windows 系统在第一次故障后不会重建，仍然可能遭受第二次故障，易损窗口随之变长。不过，一旦接到指令，Windows 的修复速度很快。

故障注入实验还揭示了 Linux、Solaris 和 Windows 2000 在其他可用性策略上的做法，涉及自动启用备用盘、重建速率、瞬时错误等方面。同样，这些系统都没有用文档说明这些策略。

故障注入实验表明，在处理瞬时故障时，Linux 的软件 RAID 实现与 Solaris、Windows 的 RAID 实现做法截然相反。Linux 的实现非常谨慎，一出现错误就以受控的方式关闭磁盘，而不是等着看这个错误是不是瞬时的。Solaris 和 Windows 则宽容得多，它们忽略大多数瞬时故障，认为这些故障不会再次发生。因此，这两个系统承受瞬时故障的能力比 Linux 强得多。不过，Windows 和 Solaris 都会把瞬时故障记入日志，所以即使不作处理，错误也会报告出来。遇到永久故障时，几个系统的行为差不多。
