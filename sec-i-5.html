计算机体系结构：量化研究方法

I.5 共享存储多处理器上科学计算应用的性能

本节讨论 I.3 节介绍的几个科学计算应用分别在对称共享存储多处理器和分布式共享存储多处理器上的性能。

对称共享存储多处理器上科学计算负载的性能

我们在一台对称共享存储多处理器上评估这四个科学计算应用的性能，问题规模如下：

  • Barnes-Hut：16 K 个物体，运行 6 个时间步（精度控制参数设为 1.0，这是一个典型的实际取值）；
  • FFT：100 万个复数数据点；
  • LU：512 × 512 的矩阵，分块大小为 16 × 16；
  • Ocean：130 × 130 的网格，采用典型的误差容限。

在分析失效率随处理器数、Cache 容量和块大小的变化时，我们把总失效率分解为一致性失效和普通的单处理器失效两部分。普通的单处理器失效包括容量失效、冲突失效和强制失效。在这几个基准测试程序中，容量失效是主要成因，因此我们把这些失效统称为容量失效。测量时，凡是把块从共享状态升级为独占状态所需的写失效，都算作一致性失效，即使实际上并没有其他处理器共享这个 Cache 块。这种计法相当于采用一种不区分私有 Cache 块和共享 Cache 块的协议。

图 I.8 给出了这四个应用的数据失效率，问题规模保持不变，处理器数从 1 增加到 16。处理器增多，Cache 总容量随之增大，通常会使容量失效减少；但处理器增多通常也会使通信量增加，进而使一致性失效增多。这两种效应的大小因应用而异。

FFT 的容量失效率下降（从将近 7% 降到略高于 5%），一致性失效率却上升（从大约 1% 升到大约 2.7%），因此总失效率基本不变。Ocean 的情况是几种效应叠加的结果，其中有些效应与网格怎样划分、网格边界怎样映射到 Cache 块有关。在典型的二维网格程序中，通信引起的失效与网格每个分区的边界长度成正比，容量失效则与网格的面积成正比。因此，问题总规模不变而 Cache 总容量增大时，受影响更大的是容量失效率，至少在每个子网格都能装进单个处理器的 Cache 之前是这样。从 1 个处理器到 2 个处理器，失效率大幅跳升，原因是多个网格映射到 Cache 的方式引起了冲突。直接映射和 2 路组相联的 Cache 中存在这种冲突，相联度更高时冲突就逐渐消失。在基于数组的应用中，这样的冲突并不少见，同时使用多个网格时尤其如此。在 Barnes 和 LU 中，处理器数增加对失效率影响很小，失效率有时略有上升，有时略有下降。

图 I.8　处理器数从 1 增加到 16 时，数据失效率可能以不直观的方式变化。失效率包括一致性失效率和容量失效率。这些基准测试程序的强制失效都非常少，已计入容量失效。这些应用中的大多数失效，都由访问可能共享的数据引起；但在失效率较高的应用（FFT 和 Ocean）中，失效率的主体是容量失效，而不是一致性失效。所谓数据可能共享，是指数据分配在地址空间中用于共享数据的部分。除 Ocean 以外，其余应用中可能共享的数据都被大量共享；而 Ocean 虽然把整个网格都当作可能共享的数据对象，真正共享的只有子网格的边界。当然，由于边界会随处理器数的增加而改变（问题规模固定时），网格中被共享的部分也随之改变。Ocean 从 1 个处理器变为 2 个处理器时容量失效率反常上升，原因是访问子网格时出现了冲突失效。除 Ocean 以外，在越来越多的处理器上运行固定规模的问题时，一致性事务引起的 Cache 失效所占比例都会上升。Ocean 的一致性失效在增加处理器的初期反而下降，原因是其中大量失效是对可能共享、但实际并不共享的数据的写所有权失效。子网格开始能够装进总的 Cache（约 16 个处理器时）以后，这种效应减弱。单处理器的数据包含写升级失效：在这个协议中，即使数据实际上不共享，只要它处于共享状态，就会发生写升级失效。所有这些运行中，Cache 容量为 64 KB，2 路组相联，块大小 32 字节。注意，各基准测试程序纵轴的刻度不同，这样才能看清每个程序的行为。图内标注：Miss rate，失效率；Processor count，处理器数；Coherence miss rate，一致性失效率；Capacity miss rate，容量失效率。

增大 Cache 容量能减少代价高昂的 Cache 失效，因此通常对性能有利。图 I.9 给出了 16 个处理器时失效率随 Cache 容量增大的变化，并分别标出一致性失效和单处理器容量失效所占的部分。Cache 容量增大时，有两种效应会使失效率不下降，或者至少不像我们预期的那样快速下降：一是固有通信，二是失效率的平台期。固有通信会产生一定频度的一致性失效，这部分失效基本不受 Cache 容量增大的影响。因此，如果问题规模保持不变而增大 Cache 容量，一致性失效率最终会限制 Cache 失效率的下降。这种效应在 Barnes 中最明显，它的一致性失效率基本上就是全部失效率。

图 I.9　失效率通常随 Cache 容量增大而下降，但一致性失效会削弱这一效果。块大小为 32 字节，Cache 为 2 路组相联，处理器数固定为 16。注意，各图的刻度不同。图内标注：Miss rate，失效率；Cache size (KB)，Cache 容量（KB）；Coherence miss rate，一致性失效率；Capacity miss rate，容量失效率。

另一种效应次要一些，即容量失效率会出现暂时的平台期。如果应用程序的一部分数据已经在 Cache 中，而数据集中相当大的一部分既装不进这个 Cache，也装不进稍大一些的 Cache，就会出现平台期。以 LU 为例，很小的 Cache（约 4 KB）就能容纳内层循环使用的一对 16 × 16 的块；此后，容量失效率要等到两个矩阵都能装进 Cache，即 Cache 总容量在 4 MB 到 8 MB 之间时，才会再有大幅改善。这种效应有时称为工作集效应。FFT 在 32 KB 到 128 KB 之间也部分存在这种效应，容量失效率只下降了 0.3%。Cache 超过这一容量后，一个主要的数据结构开始驻留在 Cache 中，容量失效率随之下降得更快。以结构化方式处理大型数组的程序，常常会出现这样的平台期。

改变 Cache 失效率的另一个办法是增大块。在单处理器中，Cache 较大时，较大的块往往是最优的。在多处理器中，则有两种新的效应起作用：一是共享数据的空间局部性降低，二是伪共享可能使失效率上升。若干研究表明，共享数据的空间局部性比非共享数据差。局部性差，取较大的共享数据块就不如在单处理器中有效，因为块中的内容还没有全部访问到，这个块就被替换出去的概率更高。同样，增大块还会使伪共享可能发生得更频繁，从而使失效率上升。

图 I.10 给出了 16 个处理器、64 KB Cache 的情况下，失效率随 Cache 块增大的变化。最有意思的是 Barnes：它的失效率先下降，后来又因一致性失效增多而上升，一致性失效增多很可能是伪共享造成的。在其他基准测试程序中，增大块都会使总失效率下降。在 Ocean 和 LU 中，增大块对一致性失效率和容量失效率的影响大致相当。在 FFT 中，一致性失效率实际上比容量失效率下降得更快。原因是 FFT 中的通信经过精心组织，效率很高。在优化程度较低的程序中，可以预料伪共享会更多，共享数据的空间局部性会更差，于是行为会更接近 Barnes。

图 I.10　数据失效率随 Cache 块增大而下降。这些结果都是 16 个处理器、64 KB Cache、2 路组相联时运行的结果。各基准测试程序同样使用不同的刻度。图内标注：Miss rate，失效率；Block size (bytes)，块大小（字节）；Coherence miss rate，一致性失效率；Capacity miss rate，容量失效率。

块越长，失效率越低，这也许会让人以为选较长的块最好。但是，基于总线的多处理器，瓶颈往往在于有限的存储器带宽和总线带宽。块越大，每次失效在总线上传送的字节就越多。图 I.11 给出了总线流量随块增大而增长的情况。失效率高的程序流量增长最严重，Ocean 尤其如此。流量增长会使失效开销变长、总线竞争加剧，因而实际上可能使性能下降。

图 I.11　数据 Cache 的块增大时，数据失效引起的总线流量稳步上升。Ocean 的流量增加到原来的 3 倍，这是反对采用较大块的最有力的论据。要记住，我们的协议把所有权失效（升级失效）和其他失效同样对待，这使大 Cache 块的开销略有增加；在 Ocean 和 FFT 中，这一简化引起的流量都不到总流量的 10%。图内标注：Bytes per data reference，每次数据访问的字节数；Block size (bytes)，块大小（字节）。

分布式存储多处理器上科学计算负载的性能

基于目录的多处理器，其性能所取决的因素，许多与基于总线的多处理器相同（如 Cache 容量、处理器数和块大小）；此外还取决于失效在存储层次中各个位置上的分布。所请求的数据项位于何处，既取决于初始分配，也取决于共享模式。我们先考察这个科学/工程计算负载的基本 Cache 性能，再看不同类型失效的影响。

这台多处理器比前面基于监听的多处理器规模更大，延迟也更长，所以我们一开始就采用稍大一些的 Cache（128 KB），块也更大，为 64 字节。

在分布式存储体系结构中，存储请求在本地和远程之间怎样分布，是影响性能的关键，因为它既影响全局带宽的消耗，又影响请求所经历的延迟。因此，本节各图把 Cache 失效分成本地请求和远程请求两部分。看图时要记住，在这些应用中，远程失效大多是一致性失效；不过也有一些容量失效是远程失效，在某些数据分布不佳的应用中，这类失效可能相当多。

从图 I.12 可以看出，在这样的 Cache 容量下，失效率受处理器数变化的影响不大。唯一的例外是 Ocean，它的失效率在 64 个处理器时上升。上升的原因有两个：一是网格变小以后，Cache 中的映射冲突增多，使本地失效增加；二是一致性失效增多，而一致性失效都是远程失效。

图 I.12　在这些基准测试程序中，增加处理器时数据失效率往往保持稳定。由于网格结构，Ocean 的失效率起初下降，到 64 个处理器时又上升。Ocean 的本地失效率从 8 个处理器时的 5% 降到 32 个处理器时的 2%，到 64 个处理器时又升到 4%。Ocean 的远程失效率主要由通信驱动，从 1% 单调上升到 2.5%。注意，为了显示每个基准测试程序的具体行为，各图纵轴使用了不同的刻度。所有这些运行中，Cache 都是 128 KB，2 路组相联，块大小 64 字节。远程失效包括所有需要与另一个节点通信的失效，不论是为了取数据还是为了发送作废。特别是在这张图和本节其他数据中，远程失效的测量值包括这样的写升级失效：数据在本地存储器中是最新的，但在别处有缓存副本，因此需要发出作废。这些作废确实产生了远程流量，但是否会推迟写操作，取决于存储一致性模型。图内标注：Miss rate，失效率；Processor count，处理器数；Local misses，本地失效；Remote misses，远程失效。

图 I.13 给出了 64 个处理器、64 字节块时，失效率随 Cache 容量增大的变化。这些失效率的下降速度与我们预期的大致相同。不过，一致性失效几乎不减少，起了削弱作用，因此远程失效比本地失效下降得慢。到图中最大的 Cache 容量 512 KB 时，远程失效率已经等于或大于本地失效率。Cache 再大，这一趋势还会更加明显。

图 I.13　失效率随 Cache 容量增大而下降。本地失效率稳步下降；远程失效率的下降程度则各不相同，取决于远程失效中容量失效的成分大，还是主要由通信失效驱动。在所有情况下，本地失效率的降幅都大于远程失效率的降幅。上一小节提到的 FFT 失效率的平台期，在 Cache 超过 128 KB 后结束。这些运行使用 64 个处理器和 64 字节的 Cache 块。图内标注：Miss rate，失效率；Cache size (KB)，Cache 容量（KB）；Local misses，本地失效；Remote misses，远程失效。

图 I.14 考察了改变块大小的影响。这些应用的空间局部性好，因此即使块已经很大，再增大块也能降低失效率，只是改用最大的块带来的性能收益很小。而且，失效率的改善大部分来自本地失效的减少。

图 I.14　Cache 为 128 KB、共 64 个处理器时，数据失效率与块大小的关系。虽然从图上很难看出，但与上一小节一样，Barnes 的一致性失效率在块最大时实际上有所上升。图内标注：Miss rate，失效率；Block size (bytes)，块大小（字节）；Local misses，本地失效；Remote misses，远程失效。

图 I.15 没有直接画出存储流量，而是画出每次数据访问所需的字节数与块大小的关系，并把需求分成本地带宽和全局带宽两部分。采用总线时，只要把每个处理器的需求加起来，就得到对总线带宽和存储器带宽的总需求。采用可扩展的互连网络时，可以用图 I.15 中的数据计算每个节点所需的全局带宽，并估算对分带宽，下面的例题说明了这一点。

例题　假定一台 64 个处理器的多处理器，处理器主频为 1 GHz，每个处理器每个时钟周期持续完成一次访存。块大小为 64 字节时，远程失效率为 0.7%。求 FFT 每个节点的带宽和估算的对分带宽。假定处理器不会因远程存储请求而停顿，例如所有远程数据都已预取时就可能如此。这些带宽需求与各种互连技术相比如何？

解答　每个节点的带宽就是每次访问的数据字节数乘以访问速率：\(0.7\% \times 1\ \text{GB/s} \times 64 = 448\ \text{MB/s}\)。这一速率比 Cray T3E 硬件可持续的传输速率（使用块预取）略高，比 SGI Origin 3000 的传输速率（每对处理器 1.6 GB/s）低。FFT 每个节点的带宽需求，是最快的标准网络所能持续提供带宽的 5 倍以上。

FFT 执行全对全通信，所以对分带宽等于处理器数乘以每个节点的带宽，约为 \(64 \times 448\ \text{MB/s} = 28.7\ \text{GB/s}\)。64 个处理器的 SGI Origin 3000 对分带宽约为 50 GB/s。没有哪种标准的网络技术能接近这一水平。

上面的例题考察的是带宽需求。并行程序的另一个关键问题是远程访存时间，即延迟。为了说明这个问题，我们以一台基于目录的多处理器为简单例子。图 I.16 给出了这个简单多处理器模型所采用的参数。模型假定：本地访存取得第一个字的时间为 85 个处理器周期，通往本地存储器的通路宽 16 字节，而网络互连宽 4 字节。模型忽略了竞争的影响。在我们考察的并行基准测试程序中，竞争大概不太严重，只有采用全对全通信的 FFT 可能例外。在其他负载中，竞争可能严重影响性能。

图 I.17 给出了在图 I.16 的参数下，平均每次访存的代价（以周期计）。这里只计入了每类访问的延迟。每个柱分别标出了 Cache 命中、本地失效、远程失效和三跳远程失效的贡献。访存代价既受 Cache 失效和升级的总频度影响，也受失效在哪里得到满足的分布影响。处理器数增加时，除 Ocean 以外，远程访存的代价都相当稳定。图 I.12 清楚地表明，Ocean 在 64 个处理器时失效率上升。失效率上升，可以预料访存所花的时间也会随之增加。

图 I.17 给出的是访存代价，在这些基准测试程序中，它是多处理器的主要开销。但完整的性能模型还需要考虑存储系统中竞争的影响，以及同步延迟造成的损失。
